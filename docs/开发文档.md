# 开发文档（Phase 1–14）

按 Phase 顺序记录每一步的实现与自检结论。正文里出现的"本阶段"指当时那一步，不是当前状态。

游戏内口琴自动演奏工具的第一阶段。本阶段只做**输入通道**：把 8 个音调键 + 3 个鼠标键，
用 Windows 官方接口（`SendInput`）稳定、干净地投递出去，并且保证**任何情况下都不会留下被按住的键**。

> 本阶段不包含：热键、用户输入急停、曲谱、时间轴、播放器、GUI、录制（按需求书留给后续 Phase）。

## 1. 实现了什么

| 需求 | 落地位置 |
|---|---|
| Windows C++ 项目（C++17） | `CMakeLists.txt` / `build.bat` |
| `InputController` 统一出口 | `src\input\InputController.*` |
| 键盘输入：Z X C V B N M , | `src\input\KeyboardController.*` |
| 鼠标输入：左键 / 中键 / 右键 | `src\input\MouseController.*` |
| 6 种演奏方式 Normal/Left/Middle/Right/LeftMiddle/RightMiddle | `InputController::PressMode` / `ReleaseMode`（组合模式一次按住两个鼠标键） |
| `ReleaseAll()`（只释放 Player-owned） | `KeyboardController` / `MouseController` / `InputController` 三层都有 |
| 使用 `SendInput()` | 唯一注入点，默认走扫描码 |
| Player-owned 输入追踪 | `playerDown_[...]`，**只有发送成功才记录**，抬起后清除 |
| Input Test 测试程序 | `src\tools\input_test.cpp` → `dist\input_test.exe` |

### 关键设计点（对应需求书重点条目）

- **扫描码发送**：默认 `KEYEVENTF_SCANCODE` + `MapVirtualKeyW`，因为多数游戏通过 DirectInput / Raw Input
  读的是扫描码而不是虚拟键码。个别键取不到扫描码时自动退回虚拟键码，功能不中断。
  排障可用 `--vk` 切回虚拟键码发送。
- **注入标记**：每个事件写入 `dwExtraInfo = 0x48504C59`（ASCII `"HPLY"`）。Phase 6 的 `WH_KEYBOARD_LL`
  以 `LLKHF_INJECTED` 为主判据，这个标记是第二道保险，用于区分"本工具注入"和"别的程序注入"。
- **绝不误释放用户的键**：`ReleaseKey` / `ReleaseAll` 只处理自己记录过的输入。用户自己按住的 Shift
  永远不会进入 Player-owned 集合，因此工具停止时不会被放开（有自动测试覆盖）。
- **不重复按下**：同一键已由工具按下时，第二次 `PressKey` 直接返回 `false`，不重复下发。
- **异常安全**：`InputController` 析构即 `ReleaseAll()`；控制台 Ctrl+C / 关窗口有 handler 兜底；
  抬起失败会重试一次并记警告，然后强制清状态——不允许出现"以为按着"。
- **不阻塞**：急停路径上没有 `Sleep`、没有等待，`ReleaseAll()` 全程在一把锁内一次做完。
- **线程安全**：子控制器各自一把 mutex 保证单次按键原子；`InputController` 再加一把 `actionMutex_`
  把"按住鼠标+按键"这类多步动作和 `ReleaseAll` 整体串起来，防止急停插在组合动作中间。
- **不碰鼠标移动**：只发按键事件，`mi.dx/dy = 0` 且不带 `MOUSEEVENTF_MOVE`。

**Step 5** 选 `5`，手动按 Z X C V B N M , 和鼠标左右中键，每个键都应打印"按下"又打印"抬起"；

## 5. 已知问题

1. **中文输入法会接走注入的字母**（实测）。
   注入走的是真实扫描码，因此目标窗口如果挂着中文输入法，字母会被输入法组合成汉字
   （实测记事本里得到"自行车v不那么，"）。游戏内的口琴演奏**一般不受影响**：
   游戏窗口通常不挂输入法，且游戏读的是原始按键状态（Raw Input / DirectInput），
   不经过 IM 的文字转换。若测试菜单 3 里看到中文候选，就是这个原因，不是注入失败。
   如果后续发现有游戏受影响，可以在输入前用 `ImmAssociateContext(hwnd, NULL)` 临时摘掉
   目标窗口的输入法——但那是 Phase 11 的事，现阶段不做。

2. **鼠标点击是真实点击**，位置就是你当时的指针位置。自动测试会点左/中/右三下，跑之前把指针放到安全处。

3. **按键"已被用户按住"的边界情况**：如果用户先按住了某个键（例如 Z），工具又按下同一个键，
   停止时工具仍会释放它（按需求书第十一节实现）。`preHeldByUser_` 已经把这个事实记下来了，
   但没有改变释放策略——最坏情况是让游戏少一个持续按住，比留下卡键安全。
   是否改为"预先按住就不释放"可以做成 Phase 11 的选项。

4. **只支持本机当前键盘布局**。扫描码映射用 `MapVirtualKeyW` 按当前布局计算，
   本机实测布局号 `00000804`。换成英文布局结果一致；换成德语/法语等布局时，
   `,` 键的物理位置含义会变，需要在 Phase 11 里明确"按物理键位还是按字符"。

5. **未处理的事件**：`VK_PACKET` 注入、`SendInput` 被安全软件挂钩、多个播放线程并发等，
   都留给后续 Phase。

6. **测试辅助脚本不属于交付物**：仓库里可能还留着 `run-autotest.bat`、`notepad-e2e.sh`、
   `notepad-e2e2.sh`、`read-notepad.ps1`、`read-text-hwnd.ps1`、`diag-uia.ps1`，
   以及 `dist\*.log` 取证日志。它们是取证用的，可以删。

## 8. 关键设计点

1. **绝对时间，不是相对时间**。`Note::startTime` 是从歌曲开始算的秒数。播放调度每次都用
   `目标墙钟 = 歌曲开始时刻 + note.startTime`，**与上一个音符何时实际响过毫无关系**。
   这是"不跑拍"的根本原因，不是靠调参数调出来的。

2. **单调时钟**。所有时间都来自 `core\Time.h` 的 QPC（本机频率 `10000000 Hz`，分辨率 100 ns）。
   禁止出现 `system_clock` / `time()`：它们会被对时、夏令时、用户改系统时间影响。

3. **变速 = 时间映射**。`position = 基准位置 + 墙钟耗时 × speed`。
   所以 200% 速度不是"把每次 Sleep 除以 2"，而是走位映射天然变快；时间轴本身一个字节都不改。
   变速瞬间位置连续（实测跳变 < 0.001 ms）。

4. **自然模式抖动**：给每个音符的**原始绝对时间**叠加一个 ±3 ms 的随机偏移。
   因为偏移永远基于原始时间、不基于上一次实际时刻，所以**偏置不会累积**（实测前一半最大偏移
   2.9 ms、后一半 2.4 ms，都受同一上限约束）；总时长变化 0.02 ms；同种子结果完全可复现；
   关掉自然模式后与原谱误差为 0。

5. **三段式等待**（对应需求书第七节"播放精度与 CPU 占用的平衡"）：
   - 距目标 > 1.5 ms：高精度可等待定时器（`CreateWaitableTimerEx` + `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`），
     比 `Sleep` 准一个数量级（`Sleep(10ms)` 实测平均晚 5.98 ms，最坏晚 11.8 ms）；
   - 0.25 ~ 1.5 ms：`yield` 让出时间片；
   - < 0.25 ms：自旋。
   实测：平均绝对误差 0.000 ms、p95 0.125 ms、CPU 占用 0.00%（4 秒墙钟里几乎没耗 CPU）。

6. **播放线程优先级**。实测发现最坏的"晚醒"（几毫秒级）来自 Windows 调度抢占，而不是等待算法。
   `ScopedThreadPriorityBoost` 在等待期间把线程提到"时间关键"，析构即恢复；
   真实演奏演示里最坏延后只有 0.13 ms。

7. **时钟边界条件**（实测发现并修掉的一个真 bug）：`Stop()` 之后位置必须是 0，
   不能拿一个已清零的基准点去算"现在 - 基准点"，否则会算出开机以来的巨大秒数。
   现在 `!running_` 时位置直接取基准位置，不再碰墙钟。

## 13. 给 Phase 3 的接口约定（SongPlayer）

- **调度循环模板**（已在 `--play` 演示里跑通）：
  ```
  clock.Start(); clock.SetSpeed(speed);
  for (每个音符) {
      waiter.WaitUntil(clock.WallClockForPosition(note.startTime));   // 起音
      input->PressMode(note.mode); input->PressKey(note.key);
      waiter.WaitUntil(clock.WallClockForPosition(note.EndTime()));   // 释放
      input->ReleaseKey(note.key); input->ReleaseMode(note.mode);
  }
  input->ReleaseAll();
  ```
- **进度与游标**：用 `Timeline::LowerBound(当前位置)` / `IndexAtOrBefore` / `CountStartedBy`
  推进游标，不要在每个音符上做线性扫描（时间轴已排序，二分即可）。
- **已经过了时刻的音符**：`WaitUntil` 会立即返回一个正误差（表示迟到）。
  正确做法是**照样补发**（不跳过），下一拍仍按绝对时刻对齐；是否"丢弃迟到音符"
  留给 Phase 3 做成设置项。
- **播放器状态机**：`已停止 / 演奏中 / 已暂停`；`Stop()` 复位位置但**保留速度**（速度属于设置）。
- **播放线程**：以 `ScopedThreadPriorityBoost` 提升优先级；急停路径只调 `ReleaseAll()`，无等待。
- **时间轴是不可变的**：播放中改速度只动 `PlaybackClock::SetSpeed`，绝不重建或修改 `Timeline`。

## 15. 关键设计点

### 1. 常驻播放线程 + "命令只改意图"
`SongPlayer` 在构造时创建一个播放线程，之后一直在条件变量上等命令。按下"播放"不新建线程
（省掉毫秒级启动抖动），UI 线程只做三件事：改状态、置标志、`SetEvent` 唤醒等待。 
播放线程负责一切：推进游标、等待目标时刻、发按键、按绝对时间释放。

### 2. 急停协议：同一把锁内的「置位 + 释放」对「检查 + 发送」
这是"急停之后不可能再出现新的自动输入"的**证明依据**，而不是靠运气：

```cpp
// 播放线程：检查和发送必须在同一把锁内完成
{ std::lock_guard g(sendMutex_);
  if (stopRequested_ || pauseRequested_ || quit_) return false;   // 每次都检查
  input_.PressKey(key); }

// 命令线程（Stop / EmergencyStop / Pause）：置位和释放也在同一把锁内
{ std::lock_guard g(sendMutex_);
  stopRequested_ = true;
  input_.ReleaseAll(); }        // 此后播放线程的检查必然失败
```

若不做这一步，就会出现经典的错序：播放线程"检查通过 → 命令线程置位并释放 → 播放线程才真的按下"，
于是留下一个被一直按住的键。本项目的做法把这段竞争窗口彻底关掉：命令方最多等一次
`SendInput` 的时间（微秒级），之后按键数**只减不增**。

### 3. 可唤醒的高精度等待
`PrecisionWait` 增加了一个自动复位的唤醒事件，等待时用 `WaitForMultipleObjects(定时器, 事件)`：
- 平时表现与 Phase 2 完全一样（3000 音符零漂移那套三段式等待）；
- 一旦 `Wake()` 被调用，**正在睡的那次等待立刻返回**，播放线程马上重新判断命令。

所以暂停/急停/变速的响应时间与"距离下一个音符还有多久"无关。实测急停调用耗时：
干跑 30 轮最坏 **0.027 ms**，真注入 10 轮最坏 **1.001 ms**（真注入那次包含一次 `SendInput` 排队）。

### 4. 事件调度：起音和释放是同一套绝对时间
播放循环每一轮只做一件事，然后回到开头重读时间：

1. 释放所有 `结束时刻 ≤ 当前位置` 的已按下音符；
2. 若下一个音符的 `开始时刻 ≤ 当前位置` → 按下它（迟到也补发，不跳过），游标 +1；
3. 全部起音且手里没有按住的键 → 本曲结束；
4. 否则算出下一个事件位置（`min(下一个起音, 最早的释放)`），映射成墙钟时刻后精等到那一刻。

因为**每次**等待前都重新做时钟映射（而不是预先算死一批截止时刻），所以播放中变速、暂停、急停
都不需要重建时间轴，位置也不会跳。

### 5. 暂停必须冻结时钟
第一版只改了状态、没冻时钟，测试立刻抓出来：暂停期间位置还在往前跑（300 ms 观测到 +302.978 ms）。
现在 `Pause()` 在保存位置的同一步调用 `PlaybackClock::Pause()`，位置纹丝不动（实测 0.000 ms）。

### 6. 游标单调，不可倒退
`FiredNoteCount()` 的语义是"本曲已起音的音符数（曲内序号）"：继续演奏时从暂停位置对应的音符接着算
（`Timeline::LowerBound(暂停位置)`），**不清零**。第一版在每轮开始把计数器归零，导致继续演奏时
进度条会往回跳，也被测试当场抓出来。

### 7. 干跑模式（`dryRun`）
播放器可以只走时间轴与时钟、不注入按键。这不是测试用的补丁，而是给两类需求准备的：
自检工具量化调度精度（不用霸占你的键盘 12 秒），以及后续 Phase 7 的"预览/进度显示"。

### 8. 音符观察者（给 Phase 7 用）
`SetNoteObserver()` 在每个音符起音时回调一次（音符下标、音符、起音位置、迟到量），
回调发生在播放线程上、要求非阻塞。Phase 3 用它量出整曲每个音符的真实起音误差，
Phase 7 的音符高亮直接复用同一个回调。

## 20. 已知问题（Phase 3）

1. **暂停不补按"暂停瞬间正在响的那个音符"**：暂停会立刻释放当拍按键；继续时从暂停位置之后的
   第一个音符接着弹。长音在暂停处会断掉。这对"游戏里按一下"没有影响，若要"续上长音"，
   需要记录在飞音符的剩余时长，留到 Phase 11 的设置项。
2. **暂停/继续的采样误差**：暂停位置取自命令线程读到时钟的那一刻，与播放线程最后一次发送之间
   最多差几个微秒（实测 0.0 ms）。
3. **急停原因是"调用方给的文本"**：Phase 3 里急停的触发者是自己（演练/压力测试），
   真正的"检测到用户按键"要等 Phase 6 的低级键盘钩子把键名传进来。
4. **同一个键重叠的音符**：两个音符若在同一个键上时间重叠，第二次按下会被 Phase 1 的
   状态机拒绝（一个键只有"按下/没按下"两种状态），此时按第一次的结束时刻释放。
   内置测试曲都避免了重叠（时值 0.7×间隔）。
5. **变速后已按下的音符按原时长释放**：时长属于音符语义（打孔时间），暂时不随速度缩放。
6. **`--play` 的真实演奏需要目标窗口具有前台焦点**；若前台程序是管理员权限而工具未提权，
   `SendInput` 会被 UIPI 静默丢弃（Phase 1 自检里已有提示，Phase 7 设置页会再提示一次）。

## 24. JSON 格式（对外契约）

```json
{
    "name": "C 大调音阶",
    "bpm": 120.0,
    "timeSignature": "4/4",
    "beatUnit": "Quarter",
    "version": 1,
    "notes": [
        { "key": "Z", "mode": "Normal", "beat": 0.0, "duration": 1.0 },
        { "key": "X", "mode": "Normal", "beat": 1.0, "duration": 1.0 }
    ]
}
```

| 字段 | 必需 | 类型 | 说明 |
| --- | --- | --- | --- |
| `name` | 否 | 字符串 | 曲名；缺省"未命名"。中文直接写，文件按 UTF-8 存 |
| `bpm` | **是** | 数字 | 每分钟拍数，必须 > 0 |
| `timeSignature` | 否 | 字符串 | `"4/4"`、`"3/4"`、`"6/8"`；缺省按 4/4 处理并给一条提醒 |
| `beatUnit` | 否 | 字符串 | 一拍对应哪个时值；缺省按拍号分母推导（4/4→Quarter、6/8→Eighth） |
| `version` | 否 | 数字 | 格式版本，当前 1 |
| `notes` | **是** | 数组 | 每个元素一个音符 |
| `notes[].key` | **是** | 字符串 | `Z X C V B N M ,`（大小写都能认） |
| `notes[].mode` | 否 | 字符串 | `Normal` / `Left` / `Middle` / `Right` / `LeftMiddle` / `RightMiddle`（也认缩写 `N`/`L`/`M`/`R`/`LM`/`RM`、数字 `1`~`6`、中文 `正常`/`左键`/`中键`/`右键`/`左中`/`右中` 等）；缺省 Normal |
| `notes[].beat` | **是** | 数字 | 起音位置，单位是**拍**，从 0 开始，不能为负 |
| `notes[].duration` | 否 | 数字 | 按住时长，单位是**拍**，必须 > 0；缺省 1 拍 |

宽容与严格的分界：**影响能不能弹的一律报错**（`bpm` 缺失/非正、`notes` 缺失、按键名不认识、
`beat` 为负、`duration` 不为正）；**不影响弹奏的一律给提醒后继续**（缺 `name`/`mode`/`duration`、
缺拍号、`beatUnit` 与拍号不一致、音符数组为空）。

换算公式就是一句话：`绝对秒数 = 拍数 × 60 / BPM`。120 BPM 下 1 拍 = 0.5 秒，
所以需求书示例里 `"beat": 0.25` 的那个音符起音在 0.125 秒。

## 25. 关键设计点

1. **"拍"只在文件里存在**。保存时把绝对时间除回去（`SecondsToBeats`），加载时乘回来
   （`BeatsToSeconds`），两者严格互逆，所以"保存 → 加载"是无损的：7 首内置曲
   720 个音符实测最大时间误差 **0.000000000 ms**。播放器的代码里至今没有出现过一个"拍"字。

2. **用 `ordered_json` 而不是 `json`**。nlohmann 默认的 `json` 用 `std::map`，写出来的字段顺序是
   按字母排的（`bpm` 跑到 `name` 前面）。曲谱是要**给人手改**的文件，所以用保序的
   `ordered_json`，字段顺序与上表一致。

3. **失败不留半成品**。解析全程写在一个局部 `Song` 里，只有全部音符都成功才 `out = song`。
   任何一步出错，调用方原来的曲谱一个字节都不会变（有专门的断言覆盖）。

4. **错误消息是中文的、可定位的**。不是把 nlohmann 的英文异常直接抛给界面，而是转成
   "第 3 个音符的 `key` 无法识别：`\"Q\"`（可用：Z X C V B N M ,）"这种；JSON 语法错误会带上
   出错的字节位置；类型不对会说清"必须是数字，当前是字符串"。

5. **中文路径与中文曲名**。文件读写走 `_wfopen_s`（UTF-8 路径先转宽字符），所以
   `D:\...\dist\songs\C 大调音阶.json` 能正常写和读；曲名进文件名前会做安全化
   （`<>:"/\|?*` 与控制字符替换成 `_`，去掉首尾空格与点，限长 80 字节且不切坏 UTF-8 字符），
   "圆舞曲 3/4" 因此存成 `圆舞曲 3_4.json`。

6. **nlohmann/json 必须在 `windows.h` 之前包含**。`windows.h` 的 `min`/`max` 宏会把
   头文件里的 `std::numeric_limits<T>::max()` 展开成"宏需要 2 个参数"的编译错误。
   `SongSerializer.cpp` 的第一行就是 `#include <nlohmann/json.hpp>`，这是有意的顺序。

7. **第三方库进仓库、不加包管理器**。需求书写的是"推荐 nlohmann/json"，而它是单头文件库，
   直接放进 `third_party/` 就能编译：别人拿到源码双击 `build.bat` 一次编过，
   不需要 vcpkg、不需要联网，也不需要 CMake。

## 30. 已知问题（Phase 4）

1. **没有做"另存为"对话框**：Phase 4 是文件读写层，路径由调用方给（GUI 里就是文件对话框，
   属于 Phase 7）。测试工具默认写到 `dist\songs\`。
2. **保存会把手写的排版规范化**：字段顺序、缩进、小数写法都会按本工具的格式重写。
   手改的注释（JSON 本身不支持注释）与多余空格不会保留。
3. **文件里存的是"拍"，不是"绝对时间"**：如果 BPM 被改了，整首曲子的秒数都会跟着变，
   这是记谱的应有语义（拍谱 + BPM 决定实际时间）。要固定"秒"，就不要改 BPM。
4. **非法字符替换是单向的**：`圆舞曲 3/4` 存成 `圆舞曲 3_4.json`，从文件名反推不回原曲名
   （曲名在 JSON 的 `name` 字段里，不受影响）。
5. **未做曲谱版本迁移**：`version` 字段已经写进文件，但目前只有版本 1，加载时不做版本判断；
   将来格式变化时再补升级逻辑（需求书第三十四节的编辑器会需要）。
6. **超大曲谱没有做流式解析**：整份 JSON 一次性读进内存。600 音符实测 88 KB；
   十万音符量级（约 15 MB）才会有明显内存压力，届时再换 SAX 接口。

可以写成什么（大小写、顺序都不敏感）：

```text
F6　f6　F1–F24　Ctrl+F6　Ctrl+Shift+F9　Alt+F1　Win+A
Space　Enter　Esc　Tab　Backspace　Delete　Insert　Home　End　PageUp　PageDown
0x77（直接写虚拟键码）　none（取消绑定）
```

两条规则：

1. **两个动作不能共用一把键** —— 后设的会被拒绝，原来的设置不动。
2. **没有修饰键的字母/数字/空格可以设，但会给一句提醒** —— 注册成全局热键后，那个键在游戏里就被本工具抢走了。功能键（F1–F24）不提醒，因为需求书默认就是 F6/F7/F8。

## 34. 关键设计点

1. **热键必须注册在"会跑消息循环的那条线程"上**。`RegisterHotKey` 把 `WM_HOTKEY` 投给注册线程的消息队列，所以 `GlobalHotkeyManager` 自带一条热键线程 + `GetMessageW` 循环；运行期改键不是"就地重注册"，而是把请求 `PostThreadMessageW` 回那条线程、由它自己注销再注册。主线程只等结果（带 3 秒超时），不碰注册。
2. **加 `MOD_NOREPEAT`**。按住 F6 不放不会触发第二次，避免"长按 = 连点开始/停止"这种危险行为。
3. **回调在热键线程上执行，约定必须极短**。它只允许调用播放器命令（"改意图 + 置标志 + `SetEvent`"，实测都是微秒级），不允许文件 IO、弹窗、等待。头文件里写明了这条约定。
4. **改键失败一律回滚**。先注销旧的、再注册新的；新注册失败时把旧绑定重新注册回来，并把失败原因交回调用者。所以"改键失败"永远不会留下"这个动作没有热键"的状态（占用检测的用例专门验证了这点）。
5. **停用即放手**。`Stop()` 让热键线程自己注销全部热键再退出（跨线程 `UnregisterHotKey` 是无效的），析构也会调。所以工具退出后 F6/F7/F8 立刻还给系统。
6. **十八节的启动热键时间戳**。每次启动热键触发都记 `GetTickCount64()`，`StartHotkeyPressedRecently(700)` 就是给 Phase 6 的一句话："这次按键就是刚才那下 F6，别把它当成用户急停"。
7. **自检接口不进产品路径**。`SimulateUserKeyPress` 只服务于"验证由用户按键触发的功能"，它不参与 Player-owned 追踪、不受 `ReleaseAll()` 影响、也不加动作锁（内部有几十毫秒的"按住"时间，不能让急停等它）。产品代码里没有任何地方调用它。

## 39. 已知问题（Phase 5）

1. **热键设置目前只存在内存里**，关掉程序就回到默认三键。写入配置文件属于 Phase 11 的"配置保存"，Phase 7 的设置界面会用到 `SetHotkey`/`ResetToDefaults` 这两个接口。
2. **Win 组合键能设置但不参与自检**：注入 Win 键会弹出开始菜单，所以自检里遇到 Win 绑定直接跳过注入（解析与显示仍然测）。另外 Win+字母多半已被系统占用，注册会失败并明确报出来。
3. **占用检测只在注册时发生**：别的程序在工具运行期间抢走某个键的情况，Windows 不提供通知（已有的注册会继续有效）。用户如遇"按了没反应"，菜单 2 能看到注册状态与失败原因。
4. **`F6` 在浏览器里是"跳到地址栏"**：注入 F6 做自检时，如果前台正好是浏览器，浏览器会响应它（记事本/N 游戏不受影响）。自检注入次数很少（一轮约 10 次）。
5. **热键回调必须极短**这条约定靠纪律维持：目前唯一实现是"调播放器命令"，实测最坏 0.528 ms；将来若在回调里做别的事（存档、弹窗），会拖慢的是热键线程本身。
6. 热键是**系统级占用**：只要工具在跑，它注册的键在其它程序里也生效（这正是需求书要的效果）；退出时会立刻归还。

## 40. 给 Phase 6 的接口约定（用户输入立即停止）

> Phase 6 已按本节实现（见第 41 节起）。一处更正：`EmergencyStop` 的 detail 只填键名，
> 前缀“检测到用户输入：”由 `StopReason` 自己加，别写重（`player.EmergencyStop(event.name)`）。

Phase 6 是"用户只要主动按下任意键就立即停止自动演奏"（需求书第十四节），它需要的接口已经就位：

```cpp

if (hotkeyManager.StartHotkeyPressedRecently(700) &&
    vk == hotkeyManager.StartHotkeyVirtualKey()) {
    // 十八节：忽略这一次，不要急停
```

三条必须守住的不变量（Phase 6 不能破坏）：

1. **急停路径无等待**：钩子回调里不许加锁等待、不许 IO。`EmergencyStop()` 内部"置位 + `ReleaseAll()`"与播放线程"检查 + 发送"共用同一把发送锁，这是"急停之后不再有新的自动输入"的唯一依据。
2. **注入的输入不算用户输入**：本工具注入的按键带 `dwExtraInfo = 0x48504C59`（"HPLY"）且是 `LLKHF_INJECTED`，两者都能作为判据。
3. **别误伤用户按住的键**：`ReleaseAll()` 只放 Player-owned 的键，用户自己按住的 Shift 不受影响（Phase 1/3 的用例一直在守这条）。

## 43. 关键设计

1. **四层分开，各管一件事**：`HookTypes.h` 只有数据结构与分类语义（不含 Win32）、`InputMonitor` 管线程与钩子、`ProcessEvent` 是"分类 → 忽略判定 → 触发"的唯一分发路径、调用方（主控/UI）决定"触发之后干什么"。分类逻辑能在没有真实键盘钩子的情况下被单测，这是能自动化验证十六节的前提。
2. **自带线程 + 自己的消息循环**：低级钩子必须在装它的线程上跑消息循环，卸载也必须在同一条线程（跨线程 `UnhookWindowsHookEx` 无效）。与 Phase 5 的热键线程同一个理由。
3. **注入识别两道判据**（十六节）：`LLKHF_INJECTED`/`LLKHF_LOWER_IL_INJECTED`（鼠标对应 `LLMHF_*`）标志位，或 `dwExtraInfo == 0x48504C59`（本工具标记）。任意一条成立就算注入。第二道是保险：万一将来某个环节把注入标志丢了，工具自己的注入仍然不会被误认为用户输入。
4. **只认 KeyDown**：抬起不触发（十五节）；另外 KeyDown 进来时先查"是不是刚按下的启动热键"，再查"设置里这一类开着没有"，最后才触发。忽略原因分别计数，UI 与自检都能看。
5. **十八节的知识留在热键管理器里**：监控不认识 F6。调用方在 `shouldIgnore` 里问 `StartHotkeyPressedRecently(700) && vk == StartHotkeyVirtualKey()`。这样"启动热键改成什么了"只有一处真相，监控不需要知道。
6. **回调里不做决定**：`onUserInput` 只允许调一次非阻塞接口（本工程的用法是 `player.EmergencyStop(name)`）。文件 IO、弹窗、等锁一律禁止：Windows 对低级钩子有 `LowLevelHooksTimeout`（默认 300 ms），超时会**静默摘掉**这个钩子，钩子就再也不会报事件了。
7. **回调耗时用 QPC 计数换算**：`worstCallbackTicks_` 存的是 QPC 计数，不是纳秒。本机时钟 10 MHz → 1 计数 = 100 ns。直接当纳秒用会差 100 倍（踩过）。
8. **设置项用原子量**：钩子回调读设置时不加锁，`SetOptions` 随时可改也不影响正在处理的这条事件。
9. **只允许一份监控**：低级钩子是进程级的，一个进程里同时最多一个 `InputMonitor`；第二个 `Start` 会被拒绝并说明原因。停止之后可以换人装。
10. **"真人按键"这条路径的诚实做法**：Windows 会给所有程序注入的输入打上注入标志，程序**无法伪造**一条看起来像真人按下的按键。所以自动化只覆盖两件事：①真钩子收到的**真注入**必须被忽略（十六节，可全自动）；②把真实形状的事件喂进**同一段分发代码**验证十四/十五/十九/二十/二十六节。真正"用手按一下"这一步留给 `--manual` 由人确认，README 与自检输出都明确标注，不把模拟说成真人验证。

## 47. 已知问题（Phase 6）

1. **"真人按键"这条路径无法程序化验证**：Windows 的注入标志无法伪造，自动化只能证明"注入被忽略"和"同一段分发代码工作正常"。最终确认要靠 `--manual` 由人按一次键。这是设计上的诚实边界，不是缺陷。
2. **低级钩子是进程级全局的**：工具在跑的时候它会看到整个系统的键盘事件。监控只做计数与分类，不记录字符、不写日志、不上传。
3. **钩子回调有硬时限**：Windows 的 `LowLevelHooksTimeout`（默认 300 ms）超时后会静默摘钩。实测约 2 微秒，但将来谁在回调里做重活（存档、弹窗、查数据库）就会踩这条。
4. **鼠标移动默认关是刻意的**：游戏里视角微动很常见，开着会一动就停（二十五节明确要求默认关）。
5. **"伪装成硬件的合成输入"会被当成用户输入**：某些键盘驱动/宏软件在驱动层产生的输入没有注入标志，会被判为用户输入而急停。左右为难时取安全侧：宁可误停，不能不停。
6. **UIPI**：游戏若以管理员权限运行，本工具也必须管理员运行，否则钩子受同一限制（与 Phase 1 的结论一致）。
7. **`SawRealUserInput()` 一旦为真不再复位**（它不是状态，是"见过没有"的记录）；需要复位就重新 `Start`。
8. **用户按键只有"停止"没有"暂停"**：需求书十四节要的就是停止；"暂停后继续"只能靠 UI 按钮。

## 61. "一拍"的定义（Phase 8 里最容易搞错的地方）

本项目的"一拍"= **曲谱的 `beatUnit`**，不是固定的四分音符，`Song::Validate()` 强制 `beatUnit` 与拍号分母一致：

- 4/4、3/4 曲目：一拍 = 四分音符，`BeatMs` = 60000 / BPM；
- 6/8 曲目：一拍 = **八分音符**，四分音符等于 2 拍（120 BPM 下一拍 500 ms、四分 1000 ms）。

因此 `TimeSignature::BeatsPerBar()` 直接返回分子是**对的**（6/8 一小节 6 拍 = 3.000 秒），不需要按"每拍 = 四分音符"去折算。Phase 8 动手前曾怀疑这条是 bug，查了 `Validate()` 之后确认不改——**别按直觉改它**。

## 68. 文本格式的完整规则

- 一行一个音符：`[演奏方式+]键名 [时值]`；两个记号之间用空白分隔，多写内容会报错。
- 演奏方式：`Normal` / `Left` / `Middle` / `Right` / `LeftMiddle` / `RightMiddle`，缩写 `N` / `L` / `M` / `R` / `LM` / `RM`，也认数字 `2`/`3`/`4`（旧的单键编号）与 `5`/`6`（组合模式），中文认 `正常`/`左键`/`中键`/`右键`/`左中`/`中左`/`左中键`/`左键+中键` 与 `右中`/`中右`/`右中键`/`右键+中键`（全名 `LeftMiddle`/`RightMiddle` 当然也认）。
  - 单字母 `M` **只在写成 `M+键名` 时**表示中键；单独一个 `M` 是音调 M。这条与 `ParsePlayMode` 的约定一致（那边故意不认单字母 M，就是为了不打架）。
  - 组合模式的名字里自带 `+`（如 `左键+中键`），所以切分演奏方式取的是**最后一个** `+`：`左键+中键+Z` 能正确切成 `左键+中键` + `Z`。键名永远是一个记号（`Z X C V B N M ,`），不会看错。
- 键名：`Z X C V B N M ,`，另外认 `逗号` 与 `COMMA`。
- 时值：`1/1` `1/2` `1/4` `1/8` `1/16`，或 `全音符`/`二分音符`/`四分音符`/`八分音符`/`十六分音符`，或英文名、或数字 `4` —— 统一走 `ParseNoteValue`，不另写一套。
- 空行、以 `#` 或 `//` 开头的行、行尾注释都会跳过（`//` 不会误伤 `1/4` 里的单斜杠）。
- **时间由时值依次累加得到**，所以文本谱不表示休止符、也不能表达重叠音；BPM / 拍号 / 拍单位由曲头（主界面当前设置）提供。
- 认 UTF-8 BOM 与 CRLF/LF 混排；一行写错只影响那一行，会带行号报出来。

**热键与急停的边界（用户特别要求复核，查出并修掉一处真隐患）**

原实现只把“启动热键 + 按下后 700 ms 内”排除在急停之外，也就是说 F7/F8 被按下时仍会先走一趟
`EmergencyStop`，只是随后被热键动作盖过去——看着正常，实际是急停与热键在抢同一把发送锁。
现在改为 `GlobalHotkeyManager::IsBoundKey(vk)`：**任何一把绑定的热键都不算“用户输入打断演奏”**，
只有真正与演奏无关的按键（包括 8 个音符键）才触发急停。单测钉住三条：五个键都被认出、
未绑定的键（F5/F11/0）不误判、**改键之后新键立刻被认出且旧键立刻不再是**（证明依据是当前绑定，
而不是写死的 F6~F10 名单）。

一句必须说清的限制：`InputMonitor` 按 `LLKHF_INJECTED` 忽略一切注入事件（设计如此，免得工具
自己的按键与自动化把演奏停掉），所以**用 `SendKeys`/`SendInput` 的界面测试永远证明不了“用户输入
急停”这条路径**——它只能用真实按键触发。界面测试能证明的是“按热键不打断演奏、状态行没有出现
‘演奏被用户输入打断’”，排除逻辑本身由可运行的单测覆盖。

## 82. 简谱 → 曲谱生成器（tools/jianpu2score.py）

游戏里的对应关系（用户提供，与需求书一致）：

| 键盘 | Z | X | C | V | B | N | M | , |
|---|---|---|---|---|---|---|---|---|
| 口琴 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | i（高音 1） |

鼠标：左键 = 低一个八度、中键 = 升半音、右键 = 高一个八度；左键/右键能和中间**同时按住**，
于是还能叠加出"低八度 + 升半音"（`LeftMiddle`）与"高八度 + 升半音"（`RightMiddle`）两种组合
（2026-10 用户核对；`3/mi` 与 `7/si` 上方没有黑键，所以 `#3`、`#7` 落不到黑键上）。
脚本的换算表 `MODE_ASSUMPTION` 就是按这套说法写的，`#`/`b` 一律用中键升半音实现。

`tools/jianpu2score.py` 把给人看的简谱换成工具认的 JSON：

```bash
python tools/jianpu2score.py --list             # 列出内置曲目与音域
python tools/jianpu2score.py --out dist/songs   # 生成到曲谱目录
python tools/jianpu2score.py --print 小星星      # 只打印换算结果
```

简谱写法：`1..7` 本音、`i` 高音 1、`0` 休止、`-` 延长一拍、`/2` `/4` 时值减半/四分之一、
`|` 与空格只是排版；`+4`/`+i` 高一个八度、`v4`/`v1` 低一个八度，
`+#4`/`+b7`/`v#4`/`vb7` 是"八度 + 半音"（生成 `RightMiddle` / `LeftMiddle`）。
半音按"按键 + 中键升半音"实现：`#d` 按 `d` 本身，`bd` 按低一级的 `d-1`（`3→4`、`7→i`
本来只差半音，那时不加中键）。**音域自适应**：曲子超出一个八度时自动整体移调塞进 1~i，塞不进去
（跨度超过 8 个音级）如实报错、不硬凑；八度记号不参与移调（键还是同一个，只是鼠标键不同）。

内置并已生成到 `dist\songs\`：小星星(42 音符)、两只老虎(32)、欢乐颂(28)、铃儿响叮当(49)、
音阶练习(32，1~i 上下行)、口琴模式测试(16，本音/左/中/右 对照，用来核对鼠标三模式)。

**实测**：6 首都通过工具自己的装载器 `song_json_test.exe --load`（不带 `--inject` = 干跑），
干跑整曲起音数吻合（42/42、32/32、28/28、49/49、32/32）、`结束原因：歌曲播放完成`、
`演奏结束后没有残留按键`。小星星节奏核对：`Z Z B B N N B(2 拍)` 起始拍 0,1,2,3,4,5,6，末尾 48 拍
@120bpm = 24.0 秒。

### 83.6 两个坑（踩过，写下来）
- 新建窗口类必须在 WM_NCCREATE 里就把句柄存进 hwnd_：WM_CREATE 里建子控件要拿它当父窗口，否则父句柄为空、子控件全创建失败，CreateWindowEx 返回空并报错误码 1400，现象是「窗口死活打不开」。诊断办法：把 RegisterClassExW 的返回值与 GetClassInfoExW 的结果拼进错误文案，让应用用自己的状态行报原因（GUI 应用没控制台，状态行就是日志）。

## 84. 两处反馈修复：没在演奏时按键不再报"被打断" + 底部提示不再被切掉（2026-09-25）

用户反馈：①「我没开始播放就因为按键而显示了"演奏被用户输入打断，已交还控制权"」②「下面的灰色文字显示部分有时字多的话就显示不全」。

### 84.1 误报"被用户输入打断"
- 根因：App::OnUserInput（钩子线程）无条件 PostToMain(kMsgUserInput)，界面侧又无条件显示红字——没在演奏时按键也会弹。
- 修法（两道闸）：①钩子线程只在真打断了正在进行的演奏（IsPlaying/IsPaused 为真、确实调了 EmergencyStop）时才投递消息；②界面侧再确认一次 LastStopReason() == StopReason::UserInput，不是就只刷新、不弹字。
- 说明：低层键盘钩子忽略注入输入（LLKHF_INJECTED），"按真实键"这一步自动化验不了，需要人按一下确认。

### 84.2 底部提示字多被切掉
- 根因：底部状态行只有一个字高（S(20)），而 Windows 的 STATIC（SS_LEFT）对中文长句不折行——字多时直接从右边切掉，连省略号都没有。
- 修法：
  1. 状态行给两行高（主窗口 S(38)、新建曲谱窗口三行 S(57)）；主窗口高度 +26 DIP，最小高度同步 +26，免得拉扁时又截断。
  2. 新增 ui::WrapLabelText(text, 一行放得下多少字, 最多几行)：自己按显示宽度折行（半角算 0.55 字、全角算 1 字），折行点优先取标点/空格/斜杠后面（路径不会被切在中间），放不下时末尾加省略号；设置状态前先折好再写进标签。
- 实测（把 songPath 故意设成一条很长的不存在路径，逼出最长的那条提示）：状态行 id=1016，窗口内 y=802、高 38；文字含 1 个换行 → 两行；第二行以"…"结尾；折行点落在反斜杠后（`…另一个很长的目录名字\` 换行 `很长的曲谱文件名占位.json）…`）；没有半截字，红色也不再是"被打断"。底部余量很小但两行都完整可见（窗口已按内容加高）。
- 自检：ui_test 171/0（新增 8 项折行断言：短句不折、中文按宽度折、正好放下不加省略号、放不下加省略号、半角按 0.55 折算、空串仍是空串）。

## 85. 休止也能进列表、存进曲谱（2026-09-25）

用户原话：「将休止一拍改成选中后也添加进已加的乐符列表里使其能够看到并真正发挥作用」。

### 85.1 改了什么
- **点「休止一拍」按钮 = 立刻往列表里加一条休止**（原来只是把"下一个音符的位置"往后推，列表里看不见）。
- 休止行在表格里显示为：音调列写「休止」、演奏方式列写「—」、时值列照常写「一拍（0.5 秒）」；它后面的音符整体跟着往后挪。
- **存进曲谱**：休止单独存在 JSON 的 "rests" 数组里（`{"beat":1.0,"duration":1.0}`）；老文件没有这个字段照常打开，读回来还是休止行，「编辑曲谱」里同样看得见。
- **播放**：休止不进演奏列表（本来就不出声），"真正起作用"体现在后面音符的起始时间上；休止段也计进整曲时长。
- 「编辑选中行」：时值选「休止」就把该行变成休止行，点音调按钮就把它变回音符行。

### 85.2 数据模型

## 89. 录键体验：点一下就是"要重设"，原来那些热键先让位（2026-09-30）

### 89.2 录键期间把全局热键让出去（这条是真 Bug）

  - 挂起期间若真有改键请求，只记绑定不注册，等恢复时统一注册。
- 实测（已载入《铃儿响叮当》49 个音符）：录键状态下按 F6 → 框里变 `[F6]`，主状态**一点没变**（仍是"已载入上次打开的曲谱…"，没有"开始演奏"）；关窗后再按 F6 → `开始演奏：铃儿响叮当　速度 100%`，按 F7 → `已停止，位置已归零。`

### 89.3 顺带
- 挂起只影响注册；`IsBoundKey`、`StartHotkeyPressedRecently` 这类查询照旧有效。
- 写自动化脚本要存 **UTF-8 带 BOM**（`encoding="utf-8-sig"`）：PowerShell 5.1 会把无 BOM 文件按 GBK 读，中文第二个字节可能是 `\`、`{`、`}`，把引号括号撕碎，报出莫名其妙的"表达式中缺少 )"。

## §90 设置页与主页面等高 + 页面滚动

设置页原来是"内容多高窗口就多高"（约 1100 DIP），比主页面还高，屏幕矮一点就顶到任务栏。

现在：App 打开设置前把**主页面客户区高度**告进设置窗口（`SetPageClientHeight`），设置页客户区
与主页面一模一样高（实测 1238 = 1238），装不下的选项靠**竖直滚动条**看。

- 选项整体可滚：`Layout` 里所有跟随页面的控件用 `move()`（纵坐标减 `scrollY_`），分组框矩形也同步偏移。
- **底部按钮行 + 说明两行固定在下沿不滚**（`pin()`），一直能点到"应用"。
- 滚轮：压在能自己滚的控件（排除键列表、速度下拉）上时转交给它，其余情况滚页面。
  **只读编辑框不在此列**——它没有可滚内容，压在热键框上滚轮应该滚页面（实测踩过）。
- 分组框在 `OnPaint` 里按"页高 - 底栏高"裁剪，不会画到按钮行上。
- 高度不许超过工作区（`SPI_GETWORKAREA`，留 48 DIP）。

## §91 演奏方式扩到 6 种：新增"八度 + 半音"组合模式

需求：游戏里鼠标是**修饰键**（按住才临时改音高），左键 = 低一个八度、右键 = 高一个八度、
中键 = 升半音，而且**左键/右键能和中间同时按住**。原来的 4 种演奏方式（`Normal/Left/Middle/Right`）
表达不了"低八度 + 升半音""高八度 + 升半音"，于是新增两种：

| 模式 | 名字 | 鼠标 | 音高 |
|---|---|---|---|
| `LeftMiddle` | `LM` / `左中` / `中左` / `左中键` / `左键+中键` | 左键 + 中键（同时按住） | 低一个八度再升半音 |
| `RightMiddle` | `RM` / `右中` / `中右` / `右中键` / `右键+中键` | 右键 + 中键（同时按住） | 高一个八度再升半音 |

- `Types.h/.cpp`：`PlayMode` 加两个枚举（值 4、5，旧值一个没动）、`kPlayModeCount` 4 → 6、
  `kPlayModeName` / `kPlayModeDisplay`（`左中键` / `右中键`）同步；
- `MouseButtonOf(单键)` 改成 `MouseButtonsOf(模式, out[kMaxMouseButtonsPerMode])` ——
  组合模式必须能返回**两个**鼠标键，单键返回值表达不了；
- `InputController::PressMode/ReleaseMode`：组合模式在 `actionMutex_` 内**依次按下两个鼠标键**
  （先八度键后中键），释放按镜像顺序（先中键后八度键）。铁律没动：全项目唯一出口仍是
  `InputController`、只释放自己按下成功过的键、按下失败不做补救性抬起、`ReleaseAll()` 遍历
  `kMouseButtonCount` 三个鼠标键所以组合模式天然被覆盖；
- `ParsePlayMode`：数字 `5`/`6` 对应两个新模式（旧的 `1`~`4` 含义不变），英文/缩写/中文全认。
  **组合模式先比**，否则 `左键+中键` 会被 `左键` 先吃掉；`M` 单字母仍然不当中键（避免和音调 M 打架）；
- 曲谱 JSON：`mode` 直接写 `LeftMiddle` / `RightMiddle`（也认 `LM`/`RM`/`5`/`6`/中文），
  报错文案里列全 6 个名字。**`version` 仍是 1、旧名字含义不变**，旧曲谱照常加载；
- 文本谱：缩写 `LM+X` / `RM+X`，中文 `左中+V` / `左键+中键+V`；切分演奏方式改用 `rfind('+')`
  （从最后一个 `+` 切开），这样自带 `+` 的中文别名也能解析；
- 新建曲谱窗口：演奏方式按钮 4 → 6（第二行放两个组合模式），窗口高度跟着行数算，不是写死；
- 自检曲目「32 种操作全覆盖」→「**48 种操作全覆盖**」（8 键 × 6 模式），循环上界改用
  `kPlayModeCount`，以后再改枚举数量不用再动它；
- `tools/jianpu2score.py`：`MODE_ASSUMPTION` 改成 `(八度记号, 半音记号) → 模式` 的二维表，
  新增八度记号 `+`（高八度）/ `v`（低八度），于是 `+4` → `Right`、`+#4` / `+b7` → `RightMiddle`、
  `v4` → `Left`、`v#4` / `vb7` → `LeftMiddle`。半音不再借用"左右键"，一律用中键升半音：
  `#d` 按 `d` 本身、`bd` 按低一级的 `d-1`（`3→4`、`7→i` 本来只差半音，那时不加中键）；
  `b1` 比最低音还低，会明确报错而不是硬凑。内置 12 首都不含半音，所以 `--list` 输出**逐字节没变**。
